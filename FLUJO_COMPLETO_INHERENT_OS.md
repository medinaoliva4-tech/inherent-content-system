# Flujo completo actualizado - Inherent OS

Actualizado: 18-ago-2026

## 1. Objetivo del OS

El OS de Inherent no es solo un tablero de tareas. Es el sistema operativo visual para coordinar clientes, servicios, procesos internos, equipo, deadlines, assets, aprobaciones y agenda.

Debe permitir:

- Ver el estado real de cada cliente.
- Asignar un servicio a cada cliente.
- Activar automáticamente los procesos y tareas que corresponden a ese servicio.
- Ver quién es responsable de cada tarea.
- Ver deadlines y bloqueos.
- Centralizar links importantes: Drive, GitHub, Jockey, redes, ads, documentos y calendario.
- Separar tareas por usuario.
- Ver Kanban por cliente, no solo general.
- Conectar tareas importantes a Google Calendar.
- Mantener a Codex como asesor/director operativo: priorización, agenda, checklists, seguimiento y actualización del sistema.

## 2. Principio operativo

Antes de trabajar en cualquier cliente, se debe responder:

- Qué cliente es.
- Qué servicio tiene asignado.
- En qué fase del proceso está.
- Qué output concreto se necesita.
- Quién es responsable.
- Cuál es el deadline.
- Qué assets o accesos faltan.
- Qué se puede delegar.
- Qué debe aprobar Rodrigo.

Si esto no está claro, la primera tarea es aclararlo. No se produce contenido ni se diseña nada antes.

## 4. Roles de usuario

Cada persona de la empresa debe tener su propia vista de tareas.

### Rodrigo

Responsable de:

- Prioridad por cliente.
- Dirección estratégica.
- Aprobación del Núcleo.
- Aprobación de guiones clave.
- Fotos cuando aplique.
- Edición final cuando aplique.
- Aprobación de assets finales.
- Decisiones comerciales.
- Revisión de entregables importantes.

No debería cargar con:

- Buscar links.
- Ordenar carpetas.
- Reunir assets.
- Hacer listas de competidores.
- Revisar ortografía o formatos menores.
- Cargar información repetitiva.

### Apoyo operativo

Responsable de:

- Recolectar assets.
- Ordenar links y carpetas.
- Preparar competidores.
- Preparar referencias.
- Buscar creators / influencers / UGC.
- Actualizar trackers.
- Revisar faltantes.
- Preparar material para que Rodrigo decida.
- Confirmar disponibilidad, formatos, medidas o datos.

### Editor / Producción

Responsable de:

- Recibir raw.
- Organizar material crudo.
- Editar piezas según brief.
- Subir versiones para revisión.
- Aplicar cambios.
- Entregar asset final aprobado a Jockey.

### Community / Manejo

Responsable de:

- Publicar según calendario.
- Monitorear comentarios y mensajes.
- Escalar leads o preguntas importantes.
- Usar tono aprobado del Núcleo.
- Registrar aprendizajes.

### Cliente invitado

Solo debería ver:

- Entregables para revisión.
- Fechas importantes.
- Solicitudes puntuales de feedback.
- Links aprobados.

No debería ver:

- Backlog interno.
- Costos internos.
- Discusiones estratégicas no aprobadas.
- Procesos internos de Inherent.

El dashboard no debe mostrar solo contenido semanal. Debe hablar de todo lo que está sucediendo alrededor.

Métricas recomendadas:

- Clientes activos.
- Tareas abiertas.
- Entregables críticos.
- Bloqueos.
- Tareas sin responsable.
- Tareas sin deadline.
- Clientes sin assets completos.
- Piezas sin vehículo.
- Piezas sin Creator/Partner.
- Entregables para hoy.
- Entregables de esta semana.

## 15. Herramientas recomendadas

### 15.1 MVP gratis recomendado

- Google Sheets: fuente de verdad.
- HTML Dashboard: vista visual.
- Google Calendar: agenda por usuario.
- Google Drive: archivos y documentos.
- Jockey: media library.
- Codex: dirección operativa.

### 15.2 Upgrade posible

Airtable:

- Mejor para base relacional visual.
- Bueno para interfaces.
- Bueno para relaciones entre clientes, servicios, tareas, creators y assets.

ClickUp:

- Mejor si quieren todo-en-uno.
- Bueno para tareas, docs, vistas, responsables y operación del equipo.

Trello:

- Bueno para Kanban simple.
- Limitado para procesos profundos por cliente.

## 16. Rol de Codex en el OS

Codex debe funcionar como director operativo y asesor de productividad.

Puede:

- Leer la base de tareas.
- Detectar bloqueos.
- Convertir mensajes de clientes en tareas.
- Crear checklists.
- Priorizar por apalancamiento.
- Crear agendas diarias.
- Actualizar Google Calendar.
- Generar tableros HTML.
- Ayudar a crear briefs.
- Revisar si las tareas tienen owner y deadline.
- Separar lo delegable de lo que debe hacer Rodrigo.

Codex no debe:

- Inventar prioridades sin revisar el sistema.
- Crear más complejidad de la necesaria.
- Convertir todo en texto largo si puede ser tablero.
- Tratar tareas genéricas como suficientes.

## 17. Reglas de operación

- Todo cliente debe tener servicio asignado.
- Todo servicio debe activar procesos.
- Todo proceso debe tener tareas.
- Toda tarea debe tener owner.
- Toda tarea debe tener deadline o estar en backlog.
- Todo asset final debe vivir en Jockey.
- Todo calendario de contenido debe tener `Vehiculo`.
- Todo calendario de contenido debe tener `Creator/Partner`.
- Todo bloqueo debe indicar quién puede desbloquearlo.
- Todo tablero debe permitir ver estado por cliente y por usuario.
